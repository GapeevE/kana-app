# Требования к исполнителю

Прочитать перед началом любой задачи. Эти правила действуют для всех задач и имеют приоритет над привычками и умолчаниями.

## Контекст проекта

**kana-app** — приложение для изучения японской азбуки русскоязычными пользователями. Интервальные повторения по SM-2, закрытая регистрация, синхронизация прогресса между устройствами.

Полное описание: [`docs/spec.md`](../../../spec.md). Спека — источник истины. Если задача расходится со спекой, остановитесь и сообщите владельцу продукта, не выбирайте сами.

## Жёсткие правила

### Не коммитить

**Исполнитель не создаёт коммиты.** Шаг «Передать на коммит» в конце задачи означает: сообщить владельцу продукта, что задача готова, и назвать предлагаемое сообщение коммита. Коммит делает владелец.

Не выполнять `git commit`, `git push`, `git checkout`, `git reset` — никаких операций, меняющих состояние репозитория.

### Не запускать E2E-тесты

Playwright, Cypress, Puppeteer и любые инструменты автоматического тестирования интерфейса **не устанавливаются и не запускаются**. Тестирование интерфейса выполняет владелец продукта вручную.

Если задача завершается шагом «Передать на ручную проверку» — сформулируйте, что именно нужно проверить, и остановитесь. Не пытайтесь проверить сами через браузер.

### Комментарии в коде

Комментарии затрудняют чтение кода владельцу продукта. Писать их только там, где код иначе непонятен — а лучше переписать код так, чтобы он был понятен без них.

Объяснения архитектурных решений выносить в `docs/`, а не в исходники.

Задачи содержат пояснительный текст между шагами — он предназначен исполнителю и **не переносится в код** комментариями.

### Только pnpm

`pnpm add`, `pnpm dlx`, `pnpm test`. Не использовать npm или yarn — это ломает lock-файл.

## Технические ограничения

| Параметр | Значение |
|---|---|
| Пакетный менеджер | pnpm |
| TypeScript | strict, без `any` в экспортируемых сигнатурах |
| Тесты | Vitest, только для `src/core/*` |
| Язык интерфейса | русский |
| Название в шапке и `<title>` | `kana-app` |
| Чтение знаков | ромадзи, система Хэпбёрна (`shi`, `ji`, `chi`, `tsu`) |
| Направление проверки | только узнавание: знак → чтение |
| Шкала quality | 5, 4, 3, 2, 0 — значения 1 не существует |
| Идентификаторы в данных | латиница, строчные, разделитель `_` |
| Переменные окружения | `DATABASE_URL`, `AUTH_SECRET`, `INVITE_CODE` |

Кириллическая транскрипция (киридзи) в приложении не используется нигде — это решение принято сознательно, не пытайтесь её добавить.

## Что покрывается тестами

Тесты Vitest пишутся **только для `src/core/*`** — чистых функций SM-2, сборки очереди, прогрессии и пересчёта состояния. Причина: ошибка в алгоритме повторений портит прогресс пользователя месяцами и обнаруживается не сразу.

UI, серверные действия и репозитории тестами не покрываются. Не добавляйте тесты туда по своей инициативе.

## Порядок работы над задачей

1. Прочитать файл задачи целиком до начала работы.
2. Проверить, что задачи из раздела «Зависит от» выполнены.
3. Выполнять шаги по порядку. Шаги атомарны — не объединять и не пропускать.
4. Шаги с запуском тестов выполнять и смотреть результат, а не предполагать его. Шаг «убедиться, что тест падает» — обязательный: он доказывает, что тест проверяет реальное поведение.
5. Если тест падает после реализации — чинить код, а не подгонять ожидаемое значение в тесте.
6. По завершении сообщить владельцу: что сделано, результат `pnpm test` и `pnpm build`, предлагаемое сообщение коммита.

## Когда остановиться и спросить

Останавливайтесь и обращайтесь к владельцу продукта, если:

- Задача противоречит спеке
- Шаг невыполним в описанном виде (изменился API библиотеки, файл выглядит иначе)
- Требуется секрет или доступ, которого нет
- Тест не проходит, и причина не в вашем коде
- Возникает соблазн сделать «заодно» что-то, чего в задаче нет

Не додумывайте и не расширяйте объём. Задачи намеренно узкие.

## Проверка перед сдачей

```bash
pnpm test
pnpm build
```

Оба должны проходить. Если задача не трогала `src/core/*`, тесты всё равно должны оставаться зелёными — их падение означает регрессию.

## Карта проекта

```
src/
  core/          Чистая логика без React, Next.js и БД. Переиспользуется в разделе «Кандзи»
    srs/         SM-2
    session/     Очередь сессии, пересчёт по истории
    progression/ Порядок и открытие групп
  data/kana/     Датасет 208 знаков
  server/
    db/          Схема Drizzle, подключение к Neon
    auth/        Auth.js, пароли
    repository/  Доступ к данным
    actions/     Серверные действия
  features/      UI по разделам
  components/    Общие компоненты (shadcn/ui)
  app/           Роутинг Next.js
```

Принцип: `core/*` не импортирует ничего из `server/*`, `features/*`, `app/*` и не знает о React. Нарушение этого принципа — повод остановиться и спросить.
